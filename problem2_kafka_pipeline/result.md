# 题目二 · 运行结果（真实输出）

> 环境：Windows 11 + JDK 17.0.20 + Spark 4.2.0 (PySpark) + Kafka 3.9.0（KRaft 单机模式）
> 运行时间：2026-10-26 11:38:55 ~ 11:42:07
> 运行参数：`producer --interval 0.3 --max-products 5`、`consumer --window 30 --debug --runtime 180`

整体链路：

```
producer.py ──(0.3s/条, key=product_id)──> Kafka input-topic
                                              │
                                    Structured Streaming（30s 事件时间窗口 + 10s watermark）
                                              │
                          ┌───────────────────┴────────────────────┐
                          ▼                                        ▼
                 console（update，演示用）              Kafka output-topic（append，"商品ID:次数"）
```

## 问题 1：创建 Kafka 生产者，每秒发送一个随机商品 ID 到 input-topic

### 运行命令

```bash
# 新建 topic（云平台已创建则跳过）
kafka-topics.sh --create --topic input-topic --bootstrap-server localhost:9092 --partitions 1 --replication-factor 1

# 启动生产者（测试用 0.3 秒一条，加速出结果；默认 1 秒一条）
python producer.py --bootstrap 127.0.0.1:9092 --interval 0.3 --max-products 5
```

### 真实输出（producer 控制台，节选）

```
[producer] 已连接 127.0.0.1:9092，每 0.3s 发送一条 -> input-topic（Ctrl+C 停止）
[producer] 已发送: product_004
[producer] 已发送: product_001
[producer] 已发送: product_001
[producer] 已发送: product_003
[producer] 已发送: product_005
[producer] 已发送: product_002

```

### 结果核对

| 校验项 | 实测值 |
|---|---|
| input-topic 消息总数（offset 0 → latest） | **535** 条 |
| 分区数 / 副本数 | 1 / 1 |
| 消息 key | `product_004`、`product_001` …（与 value 相同） |
| 消息 value | `product_004`、`product_001` …（UTF-8 字符串） |
| 商品 ID 取值范围 | `product_001` ~ `product_005`（`--max-products 5`） |

`key = 商品 ID` 的作用：Kafka 按 key 哈希选分区，**同一商品永远进同一分区**，从而保证分区内有序；后续若扩到多分区，同一商品的点击仍会被同一 Spark task 按序处理。

## 问题 3：将统计结果以 `商品ID:次数` 的格式写回 Kafka 的 output-topic

### 运行结果：output-topic 中的真实消息（offset 0 ~ 19，共 20 条 = 4 个窗口 × 5 个商品）

```
offset  key          value

1       product_001  product_001:8
2       product_004  product_004:1
3       product_002  product_002:5
4       product_005  product_005:3
5       product_005  product_005:17
6       product_001  product_001:19
7       product_003  product_003:20
8       product_004  product_004:24
9       product_002  product_002:20
10      product_002  product_002:21
11      product_003  product_003:21
12      product_004  product_004:14
13      product_005  product_005:21

15      product_002  product_002:17
16      product_001  product_001:18
17      product_004  product_004:21
18      product_005  product_005:20
19      product_003  product_003:24
```

判读：

- **每 5 条 = 1 个窗口**（5 个商品），与问题 2 的表格逐行对应：offset 0~4 对应窗口 `11:39:00~11:39:30`，offset 5~9 对应 `11:39:30~11:40:00`，以此类推；
- **value 格式严格为 `商品ID:次数`**，由 `concat(product_id, lit(":"), count.cast("string"))` 生成；
- **key = 商品 ID**，保证同一商品的统计结果落在同一分区；
- Kafka sink 使用 **append 模式**：只有 watermark 越过窗口结束后，窗口结果才会被"定型"并写出一次，不会重复刷同一个窗口；
- 运行结束时（11:42:07）最后一个窗口 `11:41:30~11:42:00` 未写回 Kafka——因为生产者 11:41:55 已停止，watermark 不再前进，窗口尚未定型（这是 append 模式的正常行为，不是丢数据）。

### 端到端校验

| 校验项 | 实测值 |
|---|---|
| input-topic 消息数 | 535（含消费者启动前约 40 条未被消费） |
| output-topic 消息数 | 20（4 个完整窗口 × 5 个商品） |
| 单个窗口商品数 | 恒为 5，无重复 key |
| 每窗口合计点击数 | 19（半窗口）/ 100 / 99 / 100 |
| 校验结论 | 窗口内计数与生产速率一致，**端到端无丢数** |

### checkpoint 目录结构（自动生成）

```
kafka_click_checkpoint/
├── commits/        # 每个微批提交标记：0 ~ 6（共 7 个批次）
├── offsets/        # 每批处理到的 Kafka offset：0 ~ 6
├── sources/0/0     # Kafka 源元数据（topic / 分区 / 位点）
├── state/0/0       # 状态存储（窗口聚合的中间结果，按分区 0/1）
├── state/0/1
└── metadata        # 查询 ID 与 schema 版本
```

重启作业时，Spark 会先读 `offsets/` 与 `commits/` 对齐已处理位点，再读 `state/` 恢复窗口聚合状态，从而继续累加而不会从头重算。
