# 题目一：实时词频统计系统 — 解题思路与设计说明

> 对应代码：`problem1_socket_wordcount/wordcount.py`（主程序）、`mock_data_server.py`（模拟数据源）

---

## 一、题目拆解

题目给出三个**递进**的子问题，本质是在同一个流式作业上逐步加需求：

| 子问题 | 需求 | 考察点 |
|--------|------|--------|
| 问题1 | Socket 源读文本 → 统计词频，每 10 秒触发，Complete 模式输出控制台 | 流式编程模型、触发器、输出模式 |
| 问题2 | 只统计长度 3-5 个字母的单词 | 无状态转换算子（filter/length） |
| 问题3 | 结果以 Parquet 保存到 `/tmp/wordcount_output`，设置检查点 | 文件接收器、检查点、**隐藏难点**（见 §2.3） |

## 二、解题思路：把"需求关键词"翻译成 API

Structured Streaming 的核心思想是**把数据流看成一张不断追加的无界表（unbounded table）**：
写流式程序 = 像写批处理 DataFrame 一样定义"对这张表的查询"，引擎自动把它变成微批增量执行。

### 2.1 需求 → API 映射表

| 需求关键词 | 对应 API |
|-----------|----------|
| 从 localhost:9999 读文本行 | `spark.readStream.format("socket").option("host", ...).option("port", 9999).load()` |
| 一行拆成多个单词 | `split(col("value"), " ")` 得到数组 → `explode()` 拍平成多行 |
| 统计每个单词出现频率 | `groupBy("word").count()` |
| 每 10 秒触发一次计算 | `writeStream.trigger(processingTime="10 seconds")` |
| Complete 输出模式 | `writeStream.outputMode("complete")`（每次输出**全量**最新结果） |
| 过滤 3-5 字母单词 | `filter(length(col("word")).between(3, 5))` |
| 结果存 Parquet | `writeStream.format("parquet").option("path", "/tmp/wordcount_output")` |
| 设置检查点 | `.option("checkpointLocation", "/tmp/wordcount_checkpoint")` |

### 2.2 为什么问题 1/2 用 Complete 模式

- Complete 模式每次触发输出**完整词频表**，迟到/新数据自然体现在下一批全量结果里，**不需要 watermark**；
- 代价是聚合状态（全量词表）常驻内存、永不清理——调试和教学场景正合适，生产上不用。

### 2.3 问题 3 的隐藏难点（本题最大的坑）

两个约束叠加：

1. **文件不可变**：Parquet 文件写死后不能改 → File Sink **只支持 Append 模式**（Complete 模式会报错）；
2. **Append + 流式聚合 = 必须有 watermark**：Append 要求"输出过的行永远正确"，Spark 必须确定某窗口**不再变化**才能输出。watermark（= 最大事件时间 − 容忍延迟）就是"窗口已终结"的判据，不加会直接抛异常：
   `Append output mode not supported when there are streaming aggregations ... without watermark`

所以问题 3 的实现要**换统计口径**：从"全量词频"改为"**事件时间窗口内词频**"：
`withWatermark("event_time", "20 seconds") → groupBy(window(event_time, "10 seconds"), word).count() → outputMode("append")`

### 2.4 一个容易忽略的兼容性问题（本地实测发现）

- **Spark 3.x** 的 socket 源自带 `timestamp` 列（数据接收时刻），可直接作事件时间；
- **Spark 4.x** 移除了该列，schema 只剩 `value`。

代码里做了运行时判断：有 `timestamp` 列就用它，否则用 `current_timestamp()`（处理时间）兜底，两个版本都能跑。

## 三、整体架构

```
                     ┌───────────────────────────────────────────────────────────┐
        TCP:9999     │                Spark Structured Streaming 微批循环          │
┌──────────────┐     │                                                           │
│  数据源        │     │   ┌──────────┐    ┌───────────────────┐    ┌───────────┐  │
│ nc -lk 9999  │ ──> │   │ Source    │──> │ 处理层             │──> │ Sink      │  │
│ 或            │     │   │ socket    │    │ 1. split+explode  │    │ console   │  │
│ mock_data_   │     │   │ (value,   │    │ 2. filter 3≤len≤5 │    │ (complete)│  │
│ server.py    │     │   │  timestamp│    │ 3. groupBy.count  │    │ 或        │  │
└──────────────┘     │   │  列)      │    │   (有状态聚合)      │    │ parquet   │  │
                     │   └──────────┘    │ 4. watermark+窗口  │    │ (append)  │  │
                     │                   └───────────────────┘    └───────────┘  │
                     │                          │                     │          │
                     │                          ▼                     ▼          │
                     │                    State Store          checkpoint/       │
                     │                  （聚合中间状态）        offsets+commits+state│
                     └───────────────────────────────────────────────────────────┘

每个微批（10s）：① Source 报告新增数据量 → ② 增量执行查询计划 → ③ Sink 写出结果
                → ④ 位点与状态写入 checkpoint → 进入下一轮
```

## 四、主要模块

```
problem1_socket_wordcount/
├── wordcount.py         # 主程序：三种模式的完整实现，命令行入口
└── mock_data_server.py  # Windows 模拟数据源（替代 Linux 的 nc -lk 9999），每秒发一句英文
```

| 模块 | 职责 | 为什么需要 |
|------|------|-----------|
| `wordcount.py` | 建流式查询、定义转换与输出 | 作业本体 |
| `mock_data_server.py` | 监听 TCP 端口、持续发送文本行 | socket 源需要有人往 9999 端口写数据；Windows 没有 `nc`，写一个小 server 保证跨平台可复现 |

## 五、关键类/函数说明

### `wordcount.py`

| 函数 | 说明 |
|------|------|
| `build_spark(app_name)` | 创建 SparkSession；`master("local[*]")` 仅供本地调试，集群上用 spark-submit 时删除 |
| `word_count_socket(mode, host, port, output_path, checkpoint_path, runtime)` | **总控函数**，按 `mode` 分三条路径：<br>① `basic`：explode → groupBy.count → console(complete) + 10s trigger<br>② `filter`：在 ① 基础上加 `filter(length between 3,5)`<br>③ `parquet`：watermark(20s) + 窗口(10s) 聚合 → parquet(append) + checkpoint<br>`runtime>0` 时到时 `query.awaitTermination(runtime)` + `query.stop()` 优雅退出 |
| `main()` | argparse 命令行入口（`--mode/--host/--port/--output/--checkpoint/--runtime`） |

**`word_count_socket` 内部关键步骤（与代码注释一一对应）：**

1. `lines = spark.readStream.format("socket")...load()` —— Input Table，schema 为 `value`（+ Spark 3.x 的 `timestamp`）；
2. `words = lines.select(explode(split(col("value")," ")).alias("word"), 事件时间列).filter(col("word")!="")` —— 一行变 N 行，去掉切分空串；
3. basic/filter 路径：`groupBy("word").count()` → `outputMode("complete")` + `trigger(10s)` + `console`；
4. parquet 路径：`withWatermark("event_time","20 seconds") → groupBy(window(event_time,"10 seconds"), word).count()` → 展开窗口起止列 → `outputMode("append")` + `parquet` + `checkpointLocation`；
5. `query.awaitTermination()` —— 阻塞保持流式查询运行。

### `mock_data_server.py`

| 函数 | 说明 |
|------|------|
| `main(host, port, interval)` | TCP 服务端：`bind → listen → accept` 一个客户端（Spark 的 socket 源），循环发送随机英文句子（每行以 `\n` 结尾，与 socket 源按行读取的协议一致），带 `SO_REUSEADDR` 避免重启绑定失败 |

### 设计取舍说明

- **split 用单空格**（与作业框架 import 一致），切分后过滤空串——比 `\\s+` 更简单可解释；标点/大小写归一化作为已知扩展点；
- **parquet 模式保留 3-5 字母过滤**：题目说"将处理结果保存"，沿用问题 2 的口径；
- **watermark=20s、窗口=10s**：容忍乱序 20 秒，窗口粒度与触发粒度一致，结果文件每 10 秒追加一批已终结窗口。

## 六、运行与验证

```bash
# 终端1：造数据（二选一）
nc -lk 9999                        # Linux/Mac
python mock_data_server.py         # Windows

# 终端2：三种模式
python wordcount.py --mode basic     # 问题1
python wordcount.py --mode filter    # 问题2
python wordcount.py --mode parquet   # 问题3（Windows 本地加 --output D:/tmp/... --checkpoint D:/tmp/...）
```

预期输出：
- basic/filter：控制台每 10 秒打印一次全量词频表（Batch: 0, 1, 2...）；
- parquet：`/tmp/wordcount_output` 下每 10 秒生成一批 parquet 文件，可用 `spark.read.parquet(...)` 读回验证（列为 window_start / window_end / word / count）。
